# 대화 듣기 생성 문항과 서버 실시간 합성 (2026-10)

2026-10-15 작성. 소리 듣기 5단계 '대화 듣기'와 연습 '상황별 대화 듣기'는 지금 미리 합성한 문항 34개(장면 묶음 8개, `listen_curriculum.CONVO_ITEMS`·`SCENES`)만 쓴다.
이 문서는 생성형 언어 모델이 만든 대화 문항을 서버에서 합성해 섞어 쓰는 흐름을 정하고, liplab-dev와 같은 조건에서 메모리·지연·품질을 측정해
배포 이미지에 합성기를 넣을지 판정한다. 1~6절은 측정 전에 정해 커밋한 규칙이다(사전 기준). 측정 뒤에 규칙을 바꾸지 않으며, 바꿔야 할 결함이
드러나면 결과 절에 '사후 변경'으로 따로 적는다.

## 1. 배경

- 동적 문장 합성(`backend/sound_tts.py`, Supertonic 3 ONNX)은 코드만 있고 `LIPLAB_SOUND_DYNAMIC=1`일 때만 쓰며, 배포 이미지(Dockerfile)에는 합성기가 없다.
  10/7 판단은 '4GB 기계의 기존 최대 3.15GB에 합성 중 +0.72GB를 더하면 여유가 없다'였다(`docs/sound-condition.md` 6절).
- 그 뒤 아바타 백본을 int8로 바꾸고(9/27) 정렬기·채점기를 미리 변환한 int8 파일로 올려, 10/9 v15 배포에서 서버 프로세스 최고 메모리(VmHWM)는 1.75GB였다.
  10/7 판단의 전제(3.15GB)는 int8 변환 순간의 최고치였고 지금 이미지에는 그 순간이 없다. 그래서 지금 구성으로 다시 잰다.
- 동적 합성 클립은 10/7 품질 점검(`docs/sound-qa-2026-10.md`)을 거치지 않는다. 미리 합성한 클립은 전사(large-v3)·D-GOP·신호 규칙으로 고른 것이라,
  서버에서 바로 만든 클립이 같은 기준에서 얼마나 통과하는지 따로 재야 한다.

## 2. 흐름(구현 설계)

1. **문항 생성.** 연습 '상황별 대화 듣기'에서 장면을 고르거나 5단계 문항을 받을 때, 그 장면의 생성 문항이 목표 수(장면마다 6개)보다 적으면
   서버가 뒤에서 한 문항을 만든다. 생성은 `llm_service.generate_listen_convo_item`(Haiku, 지시문 5.1절)이고, 키가 없거나 하루 한도(`llm_budget`)를
   넘거나 실패하면 만들지 않는다. 응답은 요청을 기다리게 하지 않는다(그 요청에는 그때 준비된 문항만 섞는다).
2. **문항 점검(규칙).** 대사·바꾼 말·질문·보기 4개·정답 번호가 있고, 한글과 문장 부호만 쓰고(숫자는 한글로 읽은 꼴), 대사 10~45자, 바꾼 말이 대사와 다르고,
   정답 보기가 대사나 바꾼 말에 글자로 들어 있고(띄어쓰기 무시), 보기 넷이 서로 다르고, 일반화 검사 낱말(`gen_words_in`)이 어디에도 없고,
   대사·바꾼 말이 검사 문장(`TEST_FORMS`, 옛 판 포함)이나 기존 대화 문항과 같지 않아야 한다. 하나라도 어기면 버린다.
3. **합성과 실행 중 품질 게이트.** 대사와 바꾼 말을 훈련 목소리마다(목록의 마지막 검사 목소리 제외, 지금 m1·f1·m2·f2) 합성한다. 클립 하나마다
   추론 대기열(`_ml_slot`)을 한 번씩 잡아, 사용자의 채점 요청이 합성 문항 전체가 아니라 클립 하나만 기다리게 한다. 클립은 4절 게이트를 거치고,
   통과하지 못하면 두 번째 후보(10/7 점검의 c1과 같은 설정)를 만든다. 둘 다 통과하지 못하면 그 목소리는 그 문항에서 피한다.
4. **목소리 피하기.** 문항의 `avoid_voices` = 게이트에서 대사나 바꾼 말이 떨어진 목소리 ∪ 피하기 목록(`data/listen_voice_avoid.json`)에서 보기 낱말 가운데
   하나를 구별되게 내지 못한다고 적힌 목소리. 쓸 수 있는 훈련 목소리가 둘 미만이면 문항을 버린다. 화면(`ConvoTask`)은 `voiceFor`에 `avoid_voices`를
   넘겨 그 목소리를 건너뛴다.
5. **캐시와 재사용.** 소리는 기존 서버 캐시(`LIPLAB_SOUND_CACHE_DIR`, 글·목소리 키)에, 문항은 같은 폴더의 문항 저장소에 둔다. 문항 id는 대사의 찾기 키
   해시라 같은 대사는 다시 합성하지 않는다. 게이트에서 떨어진 글·목소리도 기록해 같은 글을 되풀이해 합성하지 않는다.
6. **대체.** 생성이 꺼져 있거나, 키가 없거나, 점검·게이트에서 떨어지거나, 준비된 문항이 없으면 지금과 같이 미리 합성한 장면 문항만 낸다.
   준비된 생성 문항은 연습에서 한 묶음에 최대 3개, 5단계에서 8개 중 최대 2개를 섞는다. 5단계에서 낸 생성 문항의 답은 기록하되 숙달·단계 진행에는
   넣지 않는다(정답 번호를 사람이 확인하지 않았으므로).
7. **켜기.** 생성 `LIPLAB_LISTEN_GEN=1`, 합성 `LIPLAB_SOUND_DYNAMIC=1`(둘 다 기본 끔). 합성이 켜져 있고 `LIPLAB_WARMUP=1`이면 예열이 합성기도 올린다.

## 3. 측정 대상 구성

liplab-dev 이미지(Dockerfile `WITH_ML=1`, `DGOP_MODEL=ours`)와 같은 판: Python 3.11, `requirements.txt` + torch 2.14.0 CPU 휠 + `requirements-infer.txt`
(transformers 5.17.0), 정렬기·채점기 미리 변환한 int8 파일, 아바타 백본 WavLM-large int8(빌드와 같은 `quant_int8.export_base`), 아바타 체크포인트
`kr_a4_wavlm.pt`, Whisper base(int8). 환경 변수는 `fly.dev.toml` 그대로(`BACKBONE_QUANT=int8`, `LIPLAB_WARMUP=1`, `HF_HUB_OFFLINE=1` 등)에
`LIPLAB_SOUND_DYNAMIC=1`, `LIPLAB_LISTEN_GEN=1`을 더한다. 합성기는 `supertonic==1.3.1`(모델은 패키지가 고정한 supertonic-3 판)이다.

## 4. 실행 중 품질 게이트(사전 정의)

서버에는 전사 모델을 따로 올리지 않는다(large-v3는 메모리·지연 모두 맞지 않는다). 그래서 게이트는 10/7 판정 규칙 가운데 전사 없이 계산되는 부분만 쓴다.
코드는 `backend/sound_gate.py`이고, 함수는 `scripts/sound_pod/qa_rules.py`와 같은 값을 내야 한다(시험으로 확인).

- 정리: 10/7 5절과 같다(말소리 구간 앞뒤 150 ms, 양 끝 10 ms 페이드, 활성 레벨 −24 dBFS, 최대 표본 −1 dBFS 상한). 미리 합성한 클립과 레벨·무음이 같아진다.
- 발음: 정리한 소리를 16 kHz로 바꿔 배포 정렬기·채점기로 D-GOP 표시 점수 S를 얻는다. 길이 묶음이 문장이면 S ≥ 80, 낱말이면 S ≥ 70, 한 음절이면 S ≥ 60일 때
  통과, 그 밖은 실패다(10/7 표에서 전사가 틀렸을 때 D-GOP만으로 의심에 머무는 문턱).
- 신호: 10/7 2.2절 표 그대로(앞뒤 무음 항목 제외). 빠르기 z는 `qa_ref.json`의 목소리 × 묶음 기준, 레벨 편차는 정리 전 원본 레벨과 목소리 중앙값의 차.
  문장 끝 정렬 결함 보정(10/7 사후 변경 1)도 같게 한다.
- 음절 시각: 10/7 1.4절 조건(`fix_tail_syllables` 적용 뒤).
- 등급은 세 쪽 중 가장 나쁜 것이고, **통과 등급만 쓴다**(10/7 4.1절에서 새 글에 쓴 규칙과 같다). 첫 후보(total_steps 8, speed 1.05, 시드 0)가
  통과하지 못하면 둘째 후보(total_steps 16, speed 1.05, 시드 1)를 만들고, 둘째도 통과하지 못하면 그 글·목소리는 쓰지 않는다.

## 5. 측정 방법

### 5.1 생성 지시문(앱에 넣는 글)

> 당신은 청각장애인의 소리 듣기 훈련 문제를 만듭니다. '{장면}' 장면({장소들}) 가운데 한 곳에서 실제로 들을 법한 안내나 한 마디를 한 문장(대사)으로 쓰고,
> 같은 뜻을 더 쉬운 말로 바꾼 말(1~2문장), 들은 내용을 묻는 질문 하나, 보기 4개, 정답 번호를 냅니다. 대사는 10~40자이고, 시간·요일·장소·개수처럼
> 잘못 들으면 답이 달라지는 정보가 하나 들어갑니다. 숫자는 한글로 씁니다(예: 두 시 반, 삼 층). 정답 보기는 대사나 바꾼 말에 나온 말을 그대로 씁니다.
> 오답 보기는 정답과 소리나 뜻이 비슷하지만 들은 말과 맞지 않게 씁니다. 일상에서 흔히 쓰는 쉬운 낱말을 쓰고, 영어 알파벳·숫자·이모지는 쓰지 않습니다.
> 의학적 조언이나 진단처럼 읽힐 말은 쓰지 않습니다. 이미 있는 문장(아래 목록)과 같은 내용은 피합니다.
> 반드시 JSON 한 개로만 응답: {"place": "장소", "line": "대사", "paraphrase": "바꾼 말", "question": "질문", "options": ["…","…","…","…"], "answer": 0}

### 5.2 대리 문항

유료 API를 부르지 않는다. 대신 5.1절 지시문을 받은 Claude Code가 장면마다 3개씩 24문항을 써서 `scripts/convo_tts/fixture_items.json`에 두었다
(측정 전 커밋, 바꾸지 않음). 서버는 `LIPLAB_LISTEN_GEN_FIXTURE`가 주어지면 언어 모델 대신 이 파일의 문항을 차례로 낸다(측정·시험 전용). 24문항 모두
2절 2번 규칙을 통과하고, 대사·바꾼 말 48개 가운데 미리 합성한 글은 없다. 대사 21~32자, 바꾼 말 18~31자다.

### 5.3 조건

- RunPod 리눅스 파드 한 대(A40 SECURE 우선, GPU는 품질 측정의 전사에만 쓴다). 서버는 `uvicorn main:app --workers 1`을 `taskset -c 0,1`(2코어)과
  `OMP_NUM_THREADS=2`로 띄운다. 측정 클라이언트는 다른 코어에서 HTTP로 부른다.
- 메모리는 서버 프로세스의 `/proc/PID/status` VmHWM(최고 상주)과 VmRSS를 0.2초마다 기록한다. 단위 GB는 GiB(2^30 바이트)다(배포 점검과 같다).
- 채점 음성은 미리 합성한 클립(m1, 문장 셋)을 그대로 올린다(`/api/speak/assess`, `/api/avatar/audio2face`).

### 5.4 단계(서버 1, 기본 설정 `LIPLAB_ML_CONCURRENCY=1`)

| 단계 | 내용 |
|---|---|
| P0 | 켜고 예열이 정렬기·채점기·아바타 백본·합성기를 모두 올릴 때까지 기다린다. 합성기 적재 시간과 모델 파일 크기를 적는다 |
| P1 | 발음 채점 3번, 아바타 3번(합성 없음, 지금 서버의 기준 메모리) |
| P2 | `/api/sound` 첫 합성(대리 문항 1의 대사, m1). 예열 뒤 첫 호출 지연 |
| P3 | 이어서 대리 문항 2~20의 대사(m1) 19개를 하나씩. 문장당 지연 |
| P4 | 동시: 합성 2개, 합성 3개, 합성 2개 + 채점 1개를 한꺼번에 보내 각 응답 시간과 상태 코드 |
| P5 | 생성 흐름: 장면 8개의 연습 문항을 차례로 불러 뒤 생성을 시작하고, 모든 대리 문항이 끝날 때까지 기다린다. 생성 도중 채점 3번을 보내 지연을 잰다 |
| P6 | 끝난 뒤 VmHWM, 캐시 크기, 문항 저장소 상태 |

서버 2(`LIPLAB_ML_CONCURRENCY=3`, 보고만): 새 캐시로 켜서 예열 뒤 합성 3개 동시, 합성 + 채점 + 아바타 동시를 보내 최고 메모리를 잰다.
대기열을 늘렸을 때의 최악을 보려는 것이고 판정에는 쓰지 않는다.

### 5.5 품질(전체 점검)

서버 1이 서비스에 쓴(게이트 통과) 클립 모두를 10/7 '기존 클립 점검'과 같은 방법으로 판정한다. 캐시의 Ogg Opus를 풀어 large-v3 전사(GPU),
D-GOP·음절 시각·신호(`qa_eval.py`), 판정(`qa_judge.py judge`, 기준 `qa_ref.json`, 앞뒤 무음 항목 포함)을 그대로 쓴다. 게이트에서 떨어진 클립도 측정용으로만
남겨(`LIPLAB_SOUND_KEEP_REJECTED=1`) 같은 판정을 하고 게이트와의 일치를 보고한다(보고만).

## 6. 판정 기준(사전)

| 기호 | 항목 | 기준 |
|---|---|---|
| M1 | 서버 1 전체(P0~P6) 서버 프로세스 VmHWM | ≤ 3.3 GB |
| L1 | P3 문장당 `/api/sound` 응답 시간(합성·게이트·재합성·인코딩 포함) | 중앙값 ≤ 2.5초, 최댓값 ≤ 5.0초 |
| L2 | P2 예열 뒤 첫 호출 | ≤ 6.0초 |
| C1 | P4 모든 요청 | 상태 200, 503·500 없음 |
| C2 | P4 동시 3개의 마지막 응답 | ≤ 3 × (L1 중앙값) + 1.0초 |
| C3 | P5 생성 도중 채점 응답 시간 | 각각 ≤ (P1 채점 중앙값) + (P3 문장당 최댓값) + 0.5초 |
| Q1 | 5.5절에서 서비스에 쓴 클립의 전체 점검 등급 | 통과 ≥ 90%, 실패 ≤ 2% |
| Q2 | 게이트 통과율(대사·바꾼 말 × 훈련 목소리, 둘째 후보 포함) | ≥ 85% |
| Q3 | 대리 문항 채택률(쓸 수 있는 목소리 둘 이상) | ≥ 80% |

M1·L1·L2·C1·C2·C3·Q1·Q2·Q3를 모두 만족하면 **통과**로 보고 Dockerfile·fly.dev.toml에 합성기를 넣는 변경을 준비한다(기본 끔, 환경 변수로 켬, 배포는 하지 않음).
하나라도 어기면 **미달**로 보고 이유와 대안을 적는다. 파드는 liplab-dev(fly shared-cpu)보다 코어 하나가 빠르므로(9/25 채점 2코어 파드 1.6~2.0초, fly 2.4~2.8초)
지연은 fly에서 약 1.4배로 볼 수 있다. 이 환산은 보고만 하고 판정에 쓰지 않는다. fly 루트 파일시스템 읽기(초당 약 17 MB, DEPLOY.md 9항)로 합성기 모델을
처음 읽는 시간도 크기로 계산해 보고한다(예열이 뒤에서 읽으므로 사용자 지연과는 따로다).

사람 청취 평가는 하지 않는다. 대리 문항은 언어 모델 출력이 아니라 같은 지시문으로 쓴 글이라, 실제 Haiku 출력의 점검 통과율(2절 2번)은 이 측정에 들어 있지 않다.
