# 기기 안 채점(S4)의 긴 녹음 지연: 학습 없는 해법(입력 분할·스트리밍) 시험 (사전 등록 2026-10-15)

`docs/scorer-distill-2026-10.md`(S4, 10/7)의 후속이다. 1~5절은 측정 전에 적어 따로 커밋한다. 결과는 6절 뒤에 붙인다.

## 1. 배경

- S4 학생 H(한국어 HuBERT 기반, 가중치 전용 int8 ONNX 104.6MB)는 C1~C4(608 AUC, 다른 문장 합격, 사·자·차·하 대치, 크기)를 넘고 C5 지연에서 떨어졌다
  (2스레드 95백분위 4.19초 > 3.0초). 지연 표본 100문장 가운데 30초 넘는 608 조각 7개(자르기 오류로 여러 문장이 묶인 것, 앱은 앞 30초만 채점)가
  중앙 4.23초였고, 10초 이하 90문장의 95백분위는 1.46초였다. 정제 표본의 재측정은 CPU가 달라 HOLD였다(`docs/scoring-608-recut-2026-10.md` 4.3·D4).
- 10/7 지연 기록(`lat_H_w8_t2.json`)에서 문장 시간은 소리 길이에 거의 비례한다(초당 약 0.1초, 2스레드 AMD EPYC 7763). 그래서 앱 상한 30초 녹음은
  학생에서도 약 3.5~4초가 걸린다. 지연만의 문제이므로 학습 없이 먼저 해 볼 것은 녹음하는 동안 앞부분을 미리 계산해 두는 스트리밍이다.
- 학생 가중치는 10/14 정리에서 지웠다. 다시 학습하려면 10/7과 같은 예산으로 A100 약 2시간 44분(약 4.5달러)이 들어 이 작업 상한(3달러)을 넘는다.
  ONNX 가중치 전용 int8의 계산량은 가중치 값과 무관하므로(같은 그래프, 같은 연산), **지연은 구조가 같은 모델로 잴 수 있다.** 판별력(분할이 점수를 바꾸는 정도)은
  학습된 학생 없이는 잴 수 없어, 교사(앱 채점기·정렬기)로 대리 측정만 하고 보고한다.

## 2. 방법

- **구조가 같은 학생:** `scripts/s4_distill_pod.py`의 `build_student("H")`와 같은 구성(`team-lucid/hubert-base-korean` 인코더 + 49차원 출력층 둘, 출력층은
  무작위 초기화)을 같은 `fold_weight_norm`·`quantize_weights_int8`(행렬곱 int8, 합성곱 float16)로 내보낸다. 크기가 10/7 H와 ±1% 안이어야 한다(다리 1).
- **전체 순전파(F, 지금 방식):** 녹음이 끝난 뒤 소리 전체(최대 30초)를 한 번에 넣고, 강제정렬·채점까지의 시간.
- **스트리밍(S):** 새 소리 C = 4.0초마다 [t − 2.0초, t + C + 1.0초] 창(왼쪽 문맥 2초, 오른쪽 문맥 1초)을 넣고 가운데 [t, t + C) 프레임만 남긴다. 첫 창은 왼쪽 문맥이 없다.
  녹음이 끝나면 아직 남지 않은 마지막 부분을 왼쪽 문맥 2초와 함께 한 번 넣고, 이어 붙인 로그확률 전체로 강제정렬·채점한다.
  **녹음 뒤 지연** = 마지막 창 순전파 + 강제정렬 + 채점. 녹음 중 창 하나의 순전파 시간도 잰다(실시간을 따라가는지).
- **길이:** 3, 5, 8, 10, 15, 20, 25, 30초. 소리는 A1 538 클립을 이어 붙여 만들고(소리 내용은 시간에 영향이 거의 없다), 목표 문장은 같은 클립 대본을 이어 붙인다.
  길이마다 5번(첫 번째 바퀴 전체는 데우기로 버림). 파드 CPU, ONNX Runtime 2스레드(intra-op), inter-op 1.
- **다리 2(CPU 차이):** 같은 파드에서 F를 10/7 지연 표본 100문장의 길이·목표 글자 수 분포(30초 상한)로 재고 10/7 학생 H 값과의 비를 적는다. 판정은 이 파드 CPU의
  절대값으로 하고, 10/7 CPU로 옮긴 값은 보고만 한다.
- **판별력 대리(보고만):** 교사(앱 int8 정렬기·채점기, 파드 GPU, TF32 끔)로 15~30초 이어 붙인 소리에서 S와 같은 창 나누기로 로그확률을 만들어, 전체 순전파 대비
  토큰 칩 색(초록·주황·빨강) 일치율, 문장 원점수 차, 칩 값 차를 낸다. 같은 창 나누기를 구조가 같은 학생(사전학습 인코더)에도 걸어 마지막 은닉 상태의 코사인 유사도를 낸다.

## 3. 기준(이 파드 CPU, 2스레드)

| 번호 | 기준 |
|---|---|
| L1 | S의 녹음 뒤 지연이 모든 길이에서 중앙값 ≤ 1.5초, 95백분위 ≤ 3.0초 |
| L2 | 30초에서 S의 녹음 뒤 지연 중앙값 ≤ 10초 F 중앙값 × 1.5(긴 녹음도 보통 문장만큼 빨리 끝남) |
| L3 | 녹음 중 창 하나(7초 창)의 순전파 95백분위 ≤ 2.0초(새 소리 4초를 따라가는 여유 2배) |
| 다리 1 | 구조가 같은 학생 ONNX 크기가 10/7 H(104.6MB)와 ±1% 안 |

- L1~L3을 모두 넘으면 '스트리밍으로 지연 해결 가능(구조 기준)'이다. 그래도 S4 C5의 판정을 바꾸지는 않는다. 학습된 학생이 없어 분할이 판별력(C1~C3)을 지키는지 재지
  못했고, 실제 기기(브라우저 WASM·WebGPU) 지연도 아니다.
- 하나라도 미달이면 미달 수치와 원인을 적고, 녹음 상한을 줄이는 제품 결정(예: 문장 15초) 쪽 계획을 적는다.

## 4. 다시 학습이 필요한가(비용 판단)

- 지연 해결 자체에는 학습이 필요 없다(스트리밍은 같은 모델에 창만 나눠 넣는다). 학습이 필요한 것은 (a) 지운 학생을 되살려 분할 판별력을 재는 것, (b) 브라우저 통합 전
  확인이다. 10/7 예산 그대로 다시 하면 약 4.5달러로 이 작업 상한을 넘으므로, 이번에는 하지 않고 7절에 계획만 적는다.
