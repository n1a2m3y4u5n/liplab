# 기기 안 채점(S4)의 긴 녹음 지연: 학습 없는 해법(입력 분할·스트리밍) 시험 (사전 등록 2026-10-15)

`docs/scorer-distill-2026-10.md`(S4, 10/7)의 후속이다. 1~5절은 측정 전에 적어 따로 커밋한다. 결과는 6절 뒤에 붙인다.

## 1. 배경

- S4 학생 H(한국어 HuBERT 기반, 가중치 전용 int8 ONNX 104.6MB)는 C1~C4(608 AUC, 다른 문장 합격, 사·자·차·하 대치, 크기)를 넘고 C5 지연에서 떨어졌다
  (2스레드 95백분위 4.19초 > 3.0초). 지연 표본 100문장 가운데 30초 넘는 608 조각 7개(자르기 오류로 여러 문장이 묶인 것, 앱은 앞 30초만 채점)가
  중앙 4.23초였고, 10초 이하 90문장의 95백분위는 1.46초였다. 정제 표본의 재측정은 CPU가 달라 HOLD였다(`docs/scoring-608-recut-2026-10.md` 4.3·D4).
- 10/7 지연 기록(`lat_H_w8_t2.json`)에서 문장 시간은 소리 길이에 거의 비례한다(초당 약 0.1초, 2스레드 AMD EPYC 7763). 그래서 앱 상한 30초 녹음은
  학생에서도 약 3.5~4초가 걸린다. 지연만의 문제이므로 학습 없이 먼저 해 볼 것은 녹음하는 동안 앞부분을 미리 계산해 두는 스트리밍이다.
- 학생 가중치는 10/14 정리에서 지웠다. 다시 학습하려면 10/7과 같은 예산으로 A100 약 2시간 44분(약 4.5달러)이 들어 이 작업 상한(3달러)을 넘는다.
  ONNX 가중치 전용 int8의 계산량은 가중치 값과 무관하므로(같은 그래프, 같은 연산), **지연은 구조가 같은 모델로 잴 수 있다.** 판별력(분할이 점수를 바꾸는 정도)은
  학습된 학생 없이는 잴 수 없어, 교사(앱 채점기·정렬기)로 대리 측정만 하고 보고한다.

## 2. 방법

- **구조가 같은 학생:** `scripts/s4_distill_pod.py`의 `build_student("H")`와 같은 구성(`team-lucid/hubert-base-korean` 인코더 + 49차원 출력층 둘, 출력층은
  무작위 초기화)을 같은 `fold_weight_norm`·`quantize_weights_int8`(행렬곱 int8, 합성곱 float16)로 내보낸다. 크기가 10/7 H와 ±1% 안이어야 한다(다리 1).
- **전체 순전파(F, 지금 방식):** 녹음이 끝난 뒤 소리 전체(최대 30초)를 한 번에 넣고, 강제정렬·채점까지의 시간.
- **스트리밍(S):** 새 소리 C = 4.0초마다 [t − 2.0초, t + C + 1.0초] 창(왼쪽 문맥 2초, 오른쪽 문맥 1초)을 넣고 가운데 [t, t + C) 프레임만 남긴다. 첫 창은 왼쪽 문맥이 없다.
  녹음이 끝나면 아직 남지 않은 마지막 부분을 왼쪽 문맥 2초와 함께 한 번 넣고, 이어 붙인 로그확률 전체로 강제정렬·채점한다.
  **녹음 뒤 지연** = 마지막 창 순전파 + 강제정렬 + 채점. 녹음 중 창 하나의 순전파 시간도 잰다(실시간을 따라가는지).
- **길이:** 3, 5, 8, 10, 15, 20, 25, 30초. 소리는 A1 538 클립을 이어 붙여 만들고(소리 내용은 시간에 영향이 거의 없다), 목표 문장은 같은 클립 대본을 이어 붙인다.
  길이마다 5번(첫 번째 바퀴 전체는 데우기로 버림). 파드 CPU, ONNX Runtime 2스레드(intra-op), inter-op 1.
- **다리 2(CPU 차이):** 같은 파드에서 F를 10/7 지연 표본 100문장의 길이·목표 글자 수 분포(30초 상한)로 재고 10/7 학생 H 값과의 비를 적는다. 판정은 이 파드 CPU의
  절대값으로 하고, 10/7 CPU로 옮긴 값은 보고만 한다.
- **판별력 대리(보고만):** 교사(앱 int8 정렬기·채점기, 파드 GPU, TF32 끔)로 15~30초 이어 붙인 소리에서 S와 같은 창 나누기로 로그확률을 만들어, 전체 순전파 대비
  토큰 칩 색(초록·주황·빨강) 일치율, 문장 원점수 차, 칩 값 차를 낸다. 같은 창 나누기를 구조가 같은 학생(사전학습 인코더)에도 걸어 마지막 은닉 상태의 코사인 유사도를 낸다.

## 3. 기준(이 파드 CPU, 2스레드)

| 번호 | 기준 |
|---|---|
| L1 | S의 녹음 뒤 지연이 모든 길이에서 중앙값 ≤ 1.5초, 95백분위 ≤ 3.0초 |
| L2 | 30초에서 S의 녹음 뒤 지연 중앙값 ≤ 10초 F 중앙값 × 1.5(긴 녹음도 보통 문장만큼 빨리 끝남) |
| L3 | 녹음 중 창 하나(7초 창)의 순전파 95백분위 ≤ 2.0초(새 소리 4초를 따라가는 여유 2배) |
| 다리 1 | 구조가 같은 학생 ONNX 크기가 10/7 H(104.6MB)와 ±1% 안 |

- L1~L3을 모두 넘으면 '스트리밍으로 지연 해결 가능(구조 기준)'이다. 그래도 S4 C5의 판정을 바꾸지는 않는다. 학습된 학생이 없어 분할이 판별력(C1~C3)을 지키는지 재지
  못했고, 실제 기기(브라우저 WASM·WebGPU) 지연도 아니다.
- 하나라도 미달이면 미달 수치와 원인을 적고, 녹음 상한을 줄이는 제품 결정(예: 문장 15초) 쪽 계획을 적는다.

## 4. 다시 학습이 필요한가(비용 판단)

- 지연 해결 자체에는 학습이 필요 없다(스트리밍은 같은 모델에 창만 나눠 넣는다). 학습이 필요한 것은 (a) 지운 학생을 되살려 분할 판별력을 재는 것, (b) 브라우저 통합 전
  확인이다. 10/7 예산 그대로 다시 하면 약 4.5달러로 이 작업 상한을 넘으므로, 이번에는 하지 않고 7절에 계획만 적는다.

## 6. 결과(2026-10-15, 등록 커밋 65543898 뒤)

### 6.1 실행

- 파드 A40 SECURE `0far8r521gcc0s`(CPU Intel Xeon Gold 6342, 10/7의 AMD EPYC 7763과 다름). `docs/phone-tail-2026-10.md`의 A1 덤프 뒤에 GPU 작업이 끝나고 CPU만 쓸 때 쟀다.

교사(앱 정렬기·채점기 int8)로 15~30초 이어 붙인 소리 40개(토큰 10,866개)에서 전체 순전파와 창 나누기 로그확률을 비교했다.

| 4 / 4 / 3, 같은 정규화(사후 관찰) | 83.4% | 4.0 / 7.3점 | 0.933 |

- 등록한 창으로는 칩 다섯 개 중 하나의 색이 바뀌고 문장 점수가 중앙 4.4점 달라졌다. 입력 정규화를 창마다 하지 않고 전체로 해도 거의 같아, 원인은 정규화가 아니라
  트랜스포머가 문장 전체를 보고 값을 내는 데 있다(창 문맥을 6~8초로 늘리면 줄지만 2점 안팎이 남는다). 앞 문맥 8초·뒤 4초 창의 지연은 30초에서 녹음 뒤 중앙 1.46초였다.
- 학생도 같은 구조(전체 문맥 HuBERT)라 같은 영향을 받을 것이다. 따라서 **창 나누기를 그대로 쓰면 지연은 풀리지만 점수가 바뀌어, S4 C1~C3를 다시 확인하지 않고는
  쓸 수 없다.** 점수를 지키려면 학생을 처음부터 창 단위 문맥(제한된 주의 범위·청크 학습)으로 증류해야 한다. 이것은 다시 학습이 필요한 일이다.

## 7. 결론과 계획(다시 학습은 하지 않음)

- 지연만 보면 학습 없이 풀린다. 그러나 창 나누기가 판별력을 바꾸므로, 지운 학생을 되살려도 스트리밍판은 따로 판정해야 한다.
- 다시 학습 비용: 10/7과 같은 예산(234.8시간 두 번)이면 A100 약 2시간 44분, 약 4.5달러다. 이 작업 상한 3달러를 넘어 이번에는 하지 않았다.
- 다음 등록 계획(사용자 결정이 필요):
  1. 학생을 청크 주의(예: 새 소리 4초, 왼쪽 문맥 4초, 오른쪽 문맥 1~2초만 보게 하는 주의 가리개)로 증류한다. 학습 때 창 경계를 무작위로 두어 스트리밍 추론과 같은
     조건을 만든다. 교사 목표는 지금처럼 전체 문맥 교사의 출력이다. 예산은 10/7과 같게 하고 비교용 전체 문맥 학생도 함께 학습한다(약 9달러, 두 학생).
  2. 판정: 스트리밍 추론 그대로 S4 C1~C4(608 AUC ≥ 교사 − 0.01 등)와 이 문서 L1~L3.
  3. 실제 기기(학교 노트북·태블릿, ONNX Runtime Web WASM·WebGPU)에서 같은 길이 표를 잰다.
- 학습 없이 지금 할 수 있는 대안은 녹음 상한을 줄이는 제품 결정이다. F 기준으로 이 CPU에서 15초 상한이면 95백분위 1.5초(10/7 CPU 환산 약 2.6초)다.
  다만 청각장애 화자는 말이 느려 한 문장이 15초를 넘을 수 있어(608 V2 조각 최대 15초) 상한은 문장 길이 분포를 보고 정해야 한다.

## 9. 앱 연결: 스트리밍 채점 경로(2026-10-17, 플래그 뒤 기본 끔, 판정 전)

7절 계획 1의 청크 주의 학생이 판정을 넘으면 바로 끼울 수 있게 앱 쪽 경로만 먼저 만들었다. 학생 ONNX는 아직 없어 지연·점수 결과는 없다.
판정은 7절 2단계대로 학습된 학생으로 따로 한다.

### 9.1 어디에 연결했나

- 지금 발음 채점은 서버에서 돈다(`backend/dgop_acoustic.assess_text`, torch int8 교사 두 개, `/api/speak/assess`). 브라우저의
  onnxruntime-web은 얼굴 신호 K 분류기(`lib/kModel.js`)와 독화 모델(`lib/lipreadModel.js`)에만 쓴다. 강제정렬(`ctc_align`),
  발음 규칙을 거친 자모 목표(`jamo_vocab`), D-GOP·칩 값·끝 구간 다시 나누기·말 빠르기는 모두 파이썬이라, 스트리밍도 서버에 붙였다.
  브라우저 안 실행(소리가 기기 밖으로 나가지 않는 S4 본래 목표)은 7절 3단계(실제 기기 측정) 뒤의 일이고, 이 연결로는 이루지 못한다.
- 흐름(켰을 때):
  1. 프론트(`frontend/src/lib/speakStream.js`, `pages/SpeakingPractice.jsx`): 녹음을 시작하면 `POST /api/speak/stream/start`로 세션을 연다.
     녹음기와 같은 마이크 소리(에코·잡음 억제 뒤)를 소리 없는 처리 노드로 받아 16 kHz로 바꾸고(창 씌운 sinc 리샘플러) 1초씩
     16비트 PCM으로 `POST /api/speak/stream/{id}/chunk`에 차례로 보낸다. 발성·운율 단계(지표만 씀)는 쓰지 않는다.
  2. 서버(`backend/dgop_stream.py`): 덩어리 [t, t + C)의 창 끝 (t + C + R) + 80표본(수용 영역 400표본 − 보폭 320)까지 소리가 오면
     [t − L, 창 끝]을 순전파하고 가운데 프레임만 남긴다. 창 시작이 320표본 배수라 창 안 프레임이 전역 프레임과 정확히 맞는다.
  3. 정지하면 프론트가 남은 조각을 보내고 예전처럼 webm 녹음과 함께 `/api/speak/assess`에 `stream_id`를 붙인다. 서버는 끝 무음을 자르고
     (`trim_trailing_silence`), 창 끝이 자른 곳을 넘은 덩어리를 버린 뒤 남은 부분을 왼쪽 문맥과 함께 한 번 넣는다. 이어 붙인 로짓의
     로그확률로 `dgop_acoustic.assess_outputs`가 강제정렬·채점을 한다. 이 함수는 `assess_text`와 뒷부분(구간별 D-GOP, 묵음 ㅎ, 문장 점수,
     말 빠르기, 표시 보정)을 같은 코드로 나눠 쓴다.
  4. 스트리밍 채점이 실패하면 정렬기가 설정돼 있을 때 예전 경로(`assess_text`, webm)로 다시 채점하고, 없으면 전사 경로로 넘어간다.
     응답의 `dgop.stream`에 창 수·창 시간·마지막 창 시간이 붙는다.

### 9.2 플래그와 설정

| 이름 | 기본 | 뜻 |
|---|---|---|
| `DGOP_STREAM` (서버) | 끔 | `1`일 때만 `/api/speak/stream/*`를 연다. 끄면 404이고 `stream_id`는 무시해 `/api/speak/assess`는 예전과 같다 |
| `DGOP_STREAM_MODEL` (서버) | 없음 | 학생 ONNX 경로(입력 `wav` [1, 표본], 출력 `al`·`sc` [1, 프레임, 49], `s4_distill_pod.py` 내보내기와 같은 꼴). `teacher`면 지금 정렬기·채점기를 창마다 돌린다(비교용). 비어 있으면 세션을 열지 않는다(503) |
| `DGOP_STREAM_CHUNK_S`·`_LEFT_S`·`_RIGHT_S` | 4.0·2.0·1.0 | 새 소리·왼쪽 문맥·오른쪽 문맥(초, 20 ms 단위로 반올림) |
| `DGOP_STREAM_THREADS` | 2 | ONNX Runtime intra-op 스레드(inter-op 1) |
| `DGOP_STREAM_OUTPUTS` | `al,sc` | 정렬·채점 출력 이름(없으면 그래프의 앞 두 출력) |
| `DGOP_STREAM_CALIBRATION` | ONNX 옆 `calibration.json` | 학생 표시 점수 앵커. 없으면 경고를 찍고 교사 기본 앵커를 쓴다(눈금이 달라 표시 점수가 어긋난다) |
| `VITE_DGOP_STREAM` (프론트 빌드) | 끔 | `1`일 때만 녹음 중 조각을 보낸다. 끄면 요청이 예전과 같다 |

- 세션은 서버 메모리에 둔다(서버는 워커 하나, Dockerfile). 2분 동안 쓰지 않으면 지우고 사람마다 최근 2개만 둔다. 앞 30초만 받는다.
- 학생 경로는 `onnxruntime`(파이썬)이 필요하다. 지금 `requirements-infer.txt`(liplab-dev 이미지)에는 넣지 않았다(이미지가 바뀌므로 켤 때 넣는다).

### 9.3 등록 측정(6절)과 다른 점

- 오른쪽 문맥이 아직 다 오지 않은 덩어리는 녹음 중에 돌리지 않고 마지막 창에 합친다. `stream_lat.py`는 그런 덩어리를 녹음 끝에서 잘린
  오른쪽 문맥으로 녹음 중에 돌린 것으로 쳤다(예: 8.7초 녹음의 [4, 8)초 덩어리). 실제 녹음에서는 그 소리가 오기 전에 돌릴 수 없어서다.
  그래서 마지막 창은 최대 약 L + C + R(등록 창 7초)이고, 끝 자르기로 덩어리를 버리면 그만큼 길어진다. 6절 표의 길이 가운데 3·8·10·15·20·30초는
  창 나누기가 같고, 덩어리 창 끝(4k + 1초 + 80표본)이 녹음 끝을 조금 넘는 5초·25초는 다르다(등록 2·7창, 앱 1·6창). 그래서 L1~L3은 이 경로로 다시 잰다(9.5절).
- 서버가 받는 소리는 브라우저의 압축 전 PCM이다. 예전 경로의 webm(Opus) 디코드 소리와 조금 다르다.

### 9.4 시험(모델 없이)

- `backend/test_dgop_stream.py`(55개): 합성곱처럼 국소적인 가짜 모델에서 창 설정 5가지 × 길이 8가지(0.05~30초, 덩어리 경계와 마지막
  부분 덩어리 포함)의 이어 붙인 출력이 전체 순전파와 같다. 창 전체를 보는 가짜 모델에서는 창이 소리 전체를 덮으면 전체 순전파와 비트 단위로
  같고, 아니면 등록 측정의 창과 같은 값이다. 녹음 중 창이 언제 몇 번 도는지, 끝 자르기에서 버리는 덩어리, 30초 상한, PCM 변환, 세션 주인·만료,
  국소 모델에서 세션 채점이 `assess_text`와 같은 점수·음소·시각을 내는지, 플래그 끔(404)과 켬(조각 → 채점 `dgop`)의 API 경로를 본다.
- `frontend/src/lib/speakStream.test.mjs`(8개): 플래그 기본 끔, 리샘플러 길이·크기·접힘 억제·조각 나눔 무관(48·44.1·16 kHz), PCM 변환,
  조각 차례 보내기와 실패 멈춤, 세션 실패 때 null(예전 경로).

### 9.5 7절 판정을 이 경로로 돌리는 법

1. 파드에 이 브랜치의 `backend/`와 `scripts/`를 올린다(`s4_eval_pod.py`의 BK). 학생 ONNX는 파드에만 둔다(저장소에 넣지 않는다).
2. C1~C3(판별력): `s4_eval_pod.py`에 `stream:<ONNX 경로>` 백엔드를 더했다. `assess_text`가 끝 무음을 자른 소리를 넘기면 `dgop_stream.stream_outputs`로
   창 나누기를 하므로, 앱 세션에서 자른 길이로 끝낸 것과 같은 출력이다. 예: `python scripts/s4_eval_pod.py e1 stream:runs/C/student_w8.onnx 8 out/e1_C_stream.jsonl`,
   `e2`·`dev`도 같다. 비교용 전체 문맥 학생은 `onnx:<경로>`로 같은 명령을 돈다. 창은 `DGOP_STREAM_CHUNK_S`·`_LEFT_S`·`_RIGHT_S`.
   `scripts/s4_analyze.py`는 H·X 두 학생 고르기를 포함한 10/7 판정이라, 새 등록의 고르기 규칙에 맞춰 파일 이름이나 판정 함수를 맞춘다(이번에는 고치지 않았다).
3. L1~L3(지연): `STREAM_APP=1 STREAM_ONNX=<경로> STREAM_SUFFIX=_app python scripts/phone_tail/pod/stream_lat.py latency`. 녹음 중에는 0.1초씩
   들어오는 소리로 `StreamStitcher`가 창을 돌리고, 녹음 뒤 지연은 끝 자르기 + 마지막 창 + `assess_outputs`다(앱 서버와 같은 코드).
4. 통과하면 앱에서 켜는 법(배포는 사용자 결정): 서버 `DGOP_STREAM=1`, `DGOP_STREAM_MODEL=<학생 ONNX>`, 학생 표시 보정 `calibration.json`
   (10.4절 분위수 맞추기와 같은 방법), `onnxruntime` 설치, 프론트 `VITE_DGOP_STREAM=1` 빌드. 켠 뒤 실제 녹음으로 조각 지연(조각 응답 시간)과 녹음 뒤 지연을 확인한다.

## 10. 녹음 뒤 지연 나누기와 줄이기(2026-10-21, 브랜치 speak-latency-2026-10-21, 배포 안 함)

v16(S4 켬) dev에서 녹음 뒤 지연이 5.2~6.4초였는데 마지막 창은 0.44~0.74초였다. 나머지 약 4.8초가 어디서 드는지 단계마다 쟀다.

### 10.1 측정

- 서버: `/api/speak/assess`가 단계별 시간을 `Server-Timing` 머리글과 로그 한 줄(`[TIMING] speak_assess …`)로 낸다
  (read, ml_wait, stream_tail, stream_assess 또는 dgop_full·asr, score, db, formants, coaching, coaching_save, total). 뒤에서 만든 코칭은
  `[TIMING] speak_coaching llm=…`. 프론트는 `performance.mark`로 `speak:stop` 뒤 `speak:stream-done`·`speak:score`·`speak:coaching`을 잰다(개발자 도구 Performance).
- 맥 로컬(TestClient, 실제 S4 학생 int8 ONNX 2스레드, 9.6초 합성 문장, 가짜 Claude 지연 0, 두 번씩): stream_assess 0.25~0.28초, 점수·진행도 저장(db)
  0.004~0.014초, 코칭 저장 0.002~0.003초, 서버 합계 0.27~0.30초. 마지막 1초 조각이 덩어리 창을 채우면 그 조각에서 창 하나(0.46~0.50초)가 더 돈다.
- 실제 Claude 코칭(`generate_speaking_coaching`, Haiku 5.5, 같은 문장·약한 소리 2개, 맥에서 3번): **5.42·5.58·6.14초**. 세 번째는 규칙 코칭으로 끝났다
  (영문이 섞여 다시 받은 뒤에도 섞였거나 오류, 두 번 호출). API 요청은 이 3번(재시도 포함 최대 6건)만 했다.
- 결론: dev의 남은 약 4.8초는 거의 전부 **채점 요청 안에서 기다리던 Claude 코칭 호출**이다. 그 밖은 업로드·왕복 약 0.2~0.3초(조각 응답 중앙값 0.20초)와
  마지막 조각 왕복 한 번이다. 첫 녹음은 따로 학생 ONNX 적재(dev 첫 `stream/start` 7.4초)가 걸려, 조각이 늦으면 기다림 상한 4초를 넘어 예전 경로로 떨어질 수 있었다.

### 10.2 고친 것(점수·음소·코칭 내용은 그대로)

1. **점수 먼저, 코칭은 뒤에서**: 프론트가 `coaching_async=1`을 보내면 서버는 채점·저장 뒤 코칭을 기다리지 않고 돌려준다(`coaching: null`,
   `coaching_pending: true`, `coaching_id`). 같은 함수(`_speak_coaching_text`: Claude 코칭 또는 규칙 코칭 + 억양 note + 모음 교정)를 같은 입력으로
   뒤에서 돌리고 시도 기록(`SpeakAttempt.coaching`)에도 저장한다. 프론트는 `GET /api/speak/coaching/{id}`로 받아 'DOKA의 한마디'를 채우고, 그동안
   같은 칸에 '한마디를 쓰고 있어요…'를 흐리게 보인다. 이 값을 보내지 않는 예전 클라이언트는 예전처럼 기다린다. 작업은 서버 메모리에 3분 둔다(워커 하나).
2. **마지막 조각을 채점 요청에 붙이기**: 녹음 끝에 남은 1초 미만 PCM을 따로 조각 요청으로 보내지 않고 `stream_tail`로 붙인다. 서버는 같은 세션에 같은
   순서로 넣고 채점하므로(창 위치는 표본 수로만 정해진다) 점수가 같고 왕복 한 번이 준다.
3. **학생 ONNX 예열**: `LIPLAB_WARMUP=1`이고 S4가 켜져 있으면 켜질 때 학생을 올리고 1초 무음으로 한 번 돌린다.

녹음 파일(webm) 업로드는 남겼다. 세션이 실패할 때 예전 경로로 채점하는 데 필요하고, 모음 단계 포먼트도 그 파일에서 잰다(바꾸면 값이 달라진다).
코칭은 점수·약한 소리를 입력으로 쓰므로 채점과 나란히 돌릴 수 없어, 기다리는 순서만 바꿨다.
