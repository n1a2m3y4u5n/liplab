## 1. A4 백본(WavLM-large) 가중치 int8: 채택

| 관문 | 기준 | 결과 |
|---|---|---|
| A1 jawOpen 상관(모든 프레임) | ≥ 0.995 | 0.99952 |
| A2 입 채널 상관(fp32 표준편차 ≥ 0.01인 채널) | 각 ≥ 0.99 | 최저 0.99235(mouthStretchRight) |
| A3 입 채널 평균 절대차 | 전체 ≤ 0.005, 채널별 ≤ 0.01 | 전체 0.00074, 최대 채널 0.0052(mouthPucker) |
| A4 클립별 jawOpen 최대 차 | 0.05 넘는 클립 0개 | 최댓값 0.0246 |
| A5 추론 시간 비(int8/fp32, 중앙값) | ≤ 1.20 | 1.083 [1.067, 1.093] |
| A6 이득 | 파일 ≤ 0.35배, 앱 프로세스 끝 메모리 −0.6GiB 이상 | 0.28배(1.26GB → 355MB), −872MiB |

- 앱과 같은 구성(정렬기·채점기 int8 + 아바타 백본)에서 끝 메모리 2,392 → 1,520MiB, 최고 메모리 2,658 → 1,744MiB.
- fly 루트 파일시스템(초당 약 17MB) 기준 켜질 때 백본 읽기 어림 74초 → 21초.
- 앱 반영: `quant_int8.Int8Linear.weight`(읽기 전용, WavLM 주의층이 투영 가중치를 직접 읽음), `export_base`·`load_base`(metadata
  kind=base, source), `backbone_service._load_base`(int8 폴더면 그 파일), `audio2face._backbone_location`(LIPLAB_A4_BACKBONE 또는
  같은 원본에서 만든 `models/wavlm_large_int8`), Dockerfile(빌드 때 변환하고 fp32 허브 캐시 삭제, 이미지 약 0.9GB 감소, 켜질 때와
  같은 경로로 올려 보는 빌드 점검). D-GOP(wav2vec2)는 모듈 순전파를 쓰므로 점수가 바뀌지 않는다(비트 단위 테스트 그대로 통과).
- 배포는 사용자 지시가 있을 때만 한다. 배포 뒤 `tools/cold_start_measure.sh`로 아바타가 준비되기까지의 시간과 서버 최고 메모리를 본다.

## 2. D-GOP 채점 전 앞뒤 무음 자르기: 채택하지 않음

- 규칙: 프레임 에너지로 말소리 구간을 찾아 앞뒤 200ms 여유만 남긴다(numpy만). 입력은 원본과, 앞뒤에 0.3~1.5초 잡음 구간(클립보다
  30dB 낮은 백색 잡음)을 붙인 것.
- 시간은 줄었다(잡음 붙인 입력, 자름/안 자름 0.80 [0.78, 0.83], 2.70 → 2.05초). 그러나 점수가 흔들렸다.
  - 잡음 붙인 입력에서 표시 점수 차 |Δ| ≤ 1점인 클립 64%(관문 95%).
  - 원본 입력에서 86%.
  - 음소 순위 상관 중앙값 0.79(관문 0.98).
  - 음소 칩 색이 바뀐 클립 114/120.
- 사전 해석대로 읽었다. 잡음 구간 자체가 점수를 바꾸고(원본 대비 평균 |Δ| 1.11), 자르기가 원본 쪽으로 되돌리는 경우가 65%였다.
  이것은 속도 최적화가 아니라 채점 변경이라 이번에는 넣지 않는다. 판별력(맞는 문장 대 다른 문장, 608 실발화)을 보는 사전등록을 따로 해야 한다.

## 3. 정렬기·채점기의 CNN 특징 추출 공유: 넣음(결과 동일)

- 정렬기는 채점기에서 이어받아 미세조정할 때 CNN 특징 추출부를 고정해, 두 int8 파일의 이 부분 텐서 28개가 비트 단위로 같다
  (투영·인코더·출력층은 다르다). 채점은 같은 오디오를 두 모델에 각각 넣으므로 CNN을 두 번 계산했다.
- `dgop_acoustic.share_feature_encoder`가 두 모델의 특징 추출부 가중치가 모두 같을 때만 한 벌(`SharedFeatureEncoder`)로 묶고, 바로 전과
  같은 입력이면 결과를 다시 쓴다. 모델 순전파는 그대로라 transformers 내부 순서를 흉내 내지 않는다. 가중치가 하나라도 다르면 묶지 않는다.
- 확인: 작은 모델 테스트(비트 단위 일치, CNN 한 번), 실제 int8 정렬기·채점기로 538 클립 7개(맥, 2스레드)에서 음소별 D-GOP가 같고
  `phone_confidences` 시간 중앙값 0.705 → 0.576초(−18%). 속도 최적화이면서 결과가 바뀌지 않으므로 사전등록 없이 넣었다.
