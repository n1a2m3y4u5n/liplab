# 정렬기 끝 무음 증강 재학습: 문장 끝 토큰을 입력 끝에 내는 버릇 고치기 (2026-10)

2026-10-07 작성. `docs/dgop-final-vowel-2026-10.md`(10/7 채택)의 후속이다. 그 문서는 자체 학습 자모 CTC 정렬기·채점기가 문장 끝 토큰을
말소리 안이 아니라 입력의 마지막 프레임에 내고(538 '요' 끝 92.2%, Zeroth train 95.3%, 바탕 kresnik 97.0%), 원인이 학습 자료
Zeroth train의 짧은 끝 무음(말소리 끝 뒤 중앙 14 ms)이라고 확인했다. 앱은 정렬 전 '말소리 끝 + 50 ms'에서 자르는 임시 수정(M2)으로 끝
모음이 무음에 놓이는 비율을 538 T 28.3%에서 1.3%로 줄였으나, 실제 모음 시작을 찾지는 못하고(서버 음성 '요' 음절 시작이 말소리 끝 근처
한 프레임) 608 AUC가 0.902에서 0.896으로 조금 내려갔다. 이 문서는 그 문서 4.1절의 M5(정렬기 재학습)를 수행한다.

1~7절은 파드 측정 결과를 보기 전에 적어 커밋한 사전 기준이다. 결과를 본 뒤 기준을 바꾸지 않으며, 바꿔야 할 일이 생기면 결과 절에
'사후 변경'으로 따로 적는다.

## 1. 가설

학습 발화의 앞뒤에 길이가 다른 무음·약한 잡음을 붙여 학습하면, 정렬기는 '입력이 끝났다'는 단서 대신 소리 내용으로 끝 토큰의 자리를
정하게 되어, 끝 자르기 없이도 끝 모음을 말소리 안(실제 모음 시작 근처)에 놓는다. 채점기도 같은 자료로 학습해 같은 버릇이 있으므로
(10/7 7.3절: 끝 무음이 길어도 끝 모음 naive가 높은 것은 채점기가 끝 모음 확률을 입력 끝에 두기 때문), 정렬기만 바꾸면 정렬기가 고른
구간과 채점기가 끝 모음 확률을 두는 프레임이 어긋나 끝 모음 점수가 떨어질 수 있다(10/7 M3에서 본 현상). 그래서 채점기도 같은 증강으로
이어 학습한 짝을 함께 시험한다.

## 2. 학습 변경

공통. 학습 자료는 지금과 같은 Zeroth-Korean train(22,263발화, 51.6시간), 평가 손실은 Zeroth test. 학습 표본마다 그때그때(에폭마다 다르게)
아래 증강을 건다(`scripts/train_aligner.py`의 `pad_silence`, `--pad-aug`).

| 항목 | 값 | 근거 |
|---|---|---|
| 끝에 붙이기 | 확률 0.6, 길이 균등 0.1~1.5초 | 앱 녹음은 정지 버튼으로 끝나 끝 무음이 0.1초에서 1초 넘게 다양하다. 40%는 붙이지 않아 Zeroth 그대로(짧은 끝)도 남긴다 |
| 앞에 붙이기 | 확률 0.4(끝과 독립), 길이 균등 0.05~0.8초 | 녹음 시작 무음도 다양하다. 앞 무음은 이번 결함과 직접 관계가 없어 끝보다 적게 |
| 붙이는 소리 | 20%는 디지털 무음, 80%는 가우스 잡음 | 브라우저 녹음은 잡음 게이트로 거의 0인 경우와 방 소리가 남는 경우가 모두 있다 |
| 잡음 크기 | 그 발화 10 ms 창 RMS 99백분위보다 35~65 dB 낮게(균등) | 약한 방 소리. 10/7 T 조건(클립 10백분위 RMS 수준)이 이 범위에 들어간다 |
| 순서 | 정렬기 저하(severity) 뒤에 붙인다 | 붙인 잡음은 저하하지 않는다 |
| 난수 | 데이터로더 워커마다 다른 난수열(`[시드, pid]`) | 예전 코드는 워커가 같은 난수 상태를 복사받았다. 증강을 켤 때만 바뀌고 끄면 예전과 같다 |

평균 덧붙임 길이는 약 0.65초(발화 평균 약 8.3초의 8%)다.

- **정렬기(새 a1).** 지금 정렬기와 같은 레시피(`docs/scorer-selftrain.md` 1절 A-2): 지금 채점기 fp32(`liplab-lab/models/dgop_ours_2026-09-25/scorer`,
  sha256 `6b960da4…`)에서 이어 4에폭, lr 2e-5(선형, 워밍업 300), 배치 8 × 누적 2, bf16, 저하 severity 0~4 균등, CNN 특징 추출부 동결,
  에폭마다 평가 손실이 가장 낮은 체크포인트. 바뀌는 것은 끝 무음 증강과 워커 난수뿐이다.
- **채점기(새 s1).** 지금 채점기에서 이어 2에폭, lr 2e-5(선형, 워밍업 300), 저하 없음(`--severities 0`, 채점기는 정상 발화 기준이어야 한다),
  끝 무음 증강만, CNN 특징 추출부 동결. 처음부터 다시 학습(stage1 3에폭 + stage2 12에폭, A100 2시간)하지 않고 이어 학습하는 것은
  비용 때문이며, 끝 출력 버릇이 이어 학습으로 풀리는지가 시험 대상이다.
- 두 모델 모두 특징 추출부를 동결하므로 지금 채점기와 가중치가 비트 단위로 같아 특징 추출부 공유(9/27)가 그대로 켜진다. 이를 C5에서 확인한다.
- 학습이 끝나면 파드에서 `scripts/export_int8.py`로 int8 파일을 만들고(실행 중 변환과 텐서·로짓이 같아야 통과), 모든 측정은 배포와 같은 int8로 한다.

## 3. 자료

- 538: 10/6·10/7과 같은 600클립(58명), 자기 문장 1개와 다른 문장 2개. 화자 절반은 crc32(화자) % 2.
- 608: 10/6·10/7과 같은 363문장(24명), 자기 문장 1개와 다른 문장 2개. 화자 절반은 10/6 `dgop_pairs.csv`의 것.
- 서버 음성: 지금 목록(`backend/data/sound/manifest.json`)의 m1·f2 문장 클립(한글 5음절 이상). 말소리 끝의 독립 기준은 '길이 − 150 ms'
  (sound-qa 5절). 화자 절반이 없어 늘 전체로 본다.
- 소리 조건: **R** 그대로, **T** 끝에 1.0초 잡음(10/7과 같은 정의와 시드). **Z**(1.0초 디지털 무음)는 끝 출력 위치 진단에만 쓴다.
- **독립 참조(MFA).** 끝 모음의 실제 시작은 Montreal Forced Aligner(korean_mfa 음향 모델·사전, 사전에 없는 낱말은 korean_mfa G2P)로
  R 소리를 강제정렬해 얻는다. CTC가 아닌 HMM 정렬기라 무음 음소가 따로 있어 이번 결함과 같은 기제가 없다. 538 자기 문장(한글만 있는
  문장)과 서버 음성을 정렬하고, 마지막 모음 음소('jo'처럼 활음이 붙은 모음 포함)의 시작을 '끝 모음 시작'으로 둔다. T 조건의 참조도
  같은 R 시각이다(덧붙인 소리는 뒤에만 있다). 608은 발화가 크게 달라 MFA 참조로 쓰지 않는다.
- 원자료(538·608 소리, 문장별 결과, 새 가중치)는 `liplab-lab`과 파드에만 두고 이 저장소에는 집계만 적는다.

## 5. 측정과 기준

### 5.1 측정

후보·소리 조건마다 클립의 세 목표 문장을 채점한다(GPU, TF32 끔, int8). 정의는 10/7 문서 5.1절과 같다.

- 끝 모음: 목표 자모열의 마지막 중성 토큰. **무음에 놓임** = 끝 모음 시작 − 말소리 끝 > 100 ms. 538·608은 R 소리의 말소리 끝
  (`dgop_acoustic.speech_end_seconds`), 서버 음성은 '길이 − 150 ms'.
- **시작 오차** = 우리 끝 모음 시작(정렬 구간 첫 프레임) − MFA 끝 모음 시작. 판정은 절대값의 중앙.
- 문장 점수(표시 점수), 608·538 AUC(자기 문장 대 다른 문장), 65점 맞게 말함 불합격률, 65점 다르게 말함 합격률.
- 코칭: `main._weak_phones`와 같은 규칙(내지 않는 ㅎ 제외)으로 자기 문장에서 끝 모음이 지목된 비율.
- 말 빠르기: `speak_cues.rate_pause`의 rate(앱이 받은 녹음 전체와 그 정렬). '느림' = rate < 4.08.
- 지연·크기: 파드 CPU 2스레드에서 538 6문장(T 소리) × 3바퀴(첫 바퀴 제외)의 `phone_confidences` 시간 중앙. 짝마다 다른 프로세스에서
  측정한다. int8 파일 크기, 특징 추출부 공유 여부.
- 진단(보고만): 탐욕 복호에서 끝 토큰이 마지막 두 프레임에 나온 비율(538 R·T·Z, 정렬기·채점기 넷), Zeroth test 앞 300·train 앞
  600발화에서 같은 비율(새 모델), 끝이 아닌 모음의 MFA 시작 오차, 학습 손실 기록.

### 5.2 탐색과 확인

기준은 확인 절반(538·608 화자 절반 1, 서버 음성은 전체)으로 판정한다. 탐색 절반 0은 측정 코드 점검과 보고에만 쓰고, 고를 하이퍼파라미터는
없다(학습 설정은 2절로 고정, 체크포인트는 평가 손실로 자동 선택). 탐색 절반을 보고 측정 코드의 결함을 찾으면 확인 절반을 보기 전에 고치고
사후 변경으로 적는다.

**608 정제 규칙(측정 전 추가, 10/7 학습 중).** 다른 세션의 독립 검토가 10/6 재생성 608 조각(`cuts608.json`, 363조각)의 자르기 오류를
찾았다. 20초 넘는 조각 34개 가운데 9개는 '문장 1개' 화자 9명의 유일한 조각인데 실제로는 82~332초 단어 목록 낭독이고, 25개는 11~32음절
문장이 23~52초로 잘린 것이다. 또 608 '다르게 말함' 짝 가운데 일부는 목표가 자기 문장과 같은 문장이다. 이는 결과와 무관한 객관적인
자르기·짝 오류이므로, 판정은 아래 정제본으로 한다.

- 608 조각 길이가 20초를 넘으면 뺀다(단어 목록 세션의 유일한 조각 9개와 잘못 자른 긴 조각을 모두 덮는다).
- '다르게 말함' 짝 가운데 목표가 자기 문장과 같은 문장(한글만 비교)인 짝을 뺀다(538에도 같은 규칙을 적용한다).
- 전체본(정제 전) 값도 함께 보고한다(`analyze.py --raw`). 이 규칙을 넣을 때 새 후보의 결과는 아직 없었다(파드에서 정렬기 학습 중).
  기준선 K0_t의 정제본 값은 10/7 자료로 미리 계산해 보았다(확인 절반 608: 139조각, AUC R 0.930·T 0.928, 전체본 161조각 0.851·0.850).
- C5(지연)는 538 클립으로 측정하므로 이 규칙의 영향을 받지 않는다. C3·C4·C6의 608 항목이 영향을 받는다.

재현 점검(전체본으로 한다). 확인 절반의 K0_t가 10/7 M2(50) 값(608 AUC R 0.851·T 0.850, 맞게 말함 불합격 R 28.6%·T 29.2%, 538 T 무음에 놓임 1.3%)과
0.002·0.5%p 넘게 다르면 판정 전에 원인을 찾는다(서버 음성은 목록이 바뀌었을 수 있어 새로 측정한 값을 쓴다).

### 5.3 기준(확인 절반 1, R과 T 모두)

| 기준 | 내용 |
|---|---|
| C1 시각(끝 자르기 없이) | 그 짝의 끝 자르기 끈 설정(n)에서 끝 모음 무음에 놓임: 538 ≤ 5%, 서버 음성 ≤ 5%. t 후보는 자기 설정의 서버 음성도 ≤ 5% |
| C2 실제 시작 | 끝 모음 시작 오차의 절대값 중앙 ≤ 40 ms(538, 서버 음성). MFA가 정렬한 클립이 각 80% 이상 |
| C3 실발화 분리도 | 608 AUC ≥ 같은 소리 조건 K0_t − 0.005 |
| C4 다른 문장 | 538·608 다른 문장 65점 합격 ≤ 5% |
| C5 크기·지연 | 끝 자르기를 켠 같은 조건에서 지연 중앙 ≤ K0_t × 1.10, int8 파일 크기 차 ≤ 1%, 특징 추출부 공유 켜짐 |
| C6 맞는 문장·코칭 | 맞게 말함 불합격 608 ≤ K0_t + 2%p, 538 ≤ K0_t + 1%p. 끝 모음 코칭 지목 538·608 ≤ K0_t + 2%p |
| C7 눈금 | 538 R 자기 문장 표시 점수 중앙이 K0_t ± 2.0 안, 서버 음성 R 점수 평균 ≥ K0_t − 1.0 |
| C8 말 빠르기 | 538 rate(T)/rate(R) 중앙 0.97~1.03, 538 T '느림' ≤ K0_t R + 2%p |

C1·C2는 사용자가 제시한 기준을 그대로 두었다. C6~C8은 10/7 문서의 비열등 기준(코칭·맞는 문장·말 빠르기)을 이어받았다. 10/7 M3은
시각을 고쳤지만 끝 모음 코칭 지목이 608 T 54.7%로 늘어 떨어졌으므로, 같은 실패를 막기 위해 C6에 넣었다.

### 5.4 채택 규칙

1. C1~C8을 모두 만족한 후보 가운데 A를 B보다 먼저 고른다(바꾸는 모델이 하나이고 앵커를 건드리지 않는다).
2. 같은 짝에서 n과 t가 모두 통과하면 t(끝 자르기 유지)를 고른다. 단 n의 608 T AUC가 t보다 0.005 이상 높고, n의 지연 중앙이 K0_t의
   1.25배 이하이면 n을 고른다(자르기가 깎던 AUC를 되찾는 경우).
3. 통과한 후보가 없으면 앱은 그대로 두고(K0_t) 이 문서에 부정 결과로 남긴다.
4. 계산은 `scripts/dgop_tailaug_pod/analyze.py`(이 문서와 함께 결과 전에 커밋)가 출력하는 `PICK`을 따른다.

- 끝 자르기: 뽑힌 후보가 n이면 `TAIL_TRIM_MARGIN_S`를 쓰는 자르기를 기본 끔으로 바꾸고(환경변수로 켤 수 있게), t면 그대로 둔다.
  어느 쪽이든 두 설정의 수치를 결과 절에 함께 적는다.
- 서버 음성 음절 시각 보정(`qa_rules.fix_tail_syllables`): 뽑힌 후보의 서버 음성 정렬에서 그 보정이 바꾸는 클립 비율과, '요'로 끝나는
  클립의 마지막 음절 시작이 MFA와 얼마나 다른지(새 정렬 대 지금 목록)를 보고한다. 비율이 5% 이하이면 다음 합성·점검부터 보정이
  필요 없다고 적는다. 지금 목록의 음절 시각은 이 작업에서 다시 만들지 않는다(소리와 이름이 바뀌지 않는 한 음절 시각만 바꿀 이유가
  약하다는 10/7 판단을 유지하되, 새 정렬이 목록보다 MFA에 뚜렷이 가까우면 다음 작업으로 남긴다).
- 맥에서 새 int8 파일의 sha256과 텐서 수를 확인하고, 백엔드 테스트(`test_dgop*.py test_ctc_align.py test_speak*.py`)를 돌린다.
  맥에서는 모델 추론을 하지 않는다.

## 7. 절차와 비용

- 맥: `scripts/dgop_tailaug_pod/session.sh stage`(묶음: 이 브랜치 backend, 학습·변환·측정 스크립트, 538·608·서버 음성 소리, 작업 목록).
- 파드: `session.sh launch`가 liplab-lab의 `tools/pod/pod.sh`만 불러 파드를 만든다(이름 `liplab-ta`, 상태 폴더 `.tastate`, 맥 워치독
  330분, 파드 자폭 타이머). `run.sh`는 설치 → MFA(백그라운드, CPU) → Zeroth 받기 → 배관 점검 3스텝 → 정렬기 학습 → 채점기 이어 학습 →
  int8 변환 → 재구현 점검(selftest) → 측정(main·tts·hyp·zeroth) → MFA 결과 읽기 → 지연 순서로 돈다. 끝나면 `session.sh finish`(결과·가중치
  받기 → terminate → status로 이 파드가 없어진 것을 확인). 다른 작업의 파드는 건드리지 않는다.
- GPU: A40 SECURE(시간당 약 0.49달러) 우선, 없으면 A6000·L40S SECURE. 예상 4시간 안팎, 약 2달러. **비용 상한 10달러**: 워치독 연장을
  포함해 이 파드의 누적 비용이 8달러에 이를 것으로 보이면 채점기 이어 학습을 건너뛰고(B 없음) A만 측정한다.
- 유료 API·SpeechSuper는 쓰지 않는다. 소리는 재생하지 않는다. 맥에서는 학습·추론을 하지 않는다.
