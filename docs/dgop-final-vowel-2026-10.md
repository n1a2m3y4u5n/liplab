# 문장 끝 모음 정렬 결함: D-GOP 말하기 채점에 주는 영향과 수정 (2026-10)

2026-10-07 작성. 소리 품질 점검(`docs/sound-qa-2026-10.md` 8.3절)이 서버 음성에서 찾은 정렬 결함, 곧 자체 학습 자모 CTC 정렬기
(`backend/models/dgop_ours/aligner`, int8)가 문장 끝 모음을 말소리 안에 내지 않고 강제정렬이 그 모음을 파일 끝 무음에 놓는 현상이
앱 말하기 채점(`dgop_acoustic.assess_text`)에도 있는지 확인하고, 있으면 고친다. 1~6절은 파드 측정 결과를 보기 전에 적어 커밋한
사전 기준이다. 결과를 본 뒤 기준을 바꾸지 않으며, 바꿔야 할 일이 생기면 결과 절에 '사후 변경'으로 따로 적는다.

## 1. 사전 관찰(탐색, 기존 자료)

기준을 정하기 전에 10/6 파드 결과(`liplab-lab/data/pod_runs/20261006_35zrgz6wvrqiho/sc/out`, 정렬기·채점기 로짓과 음소별 점수,
538 600클립·608 363문장)를 모델 추론 없이 다시 보았다. 말소리 끝은 10 ms 창 RMS가 max(99백분위 − 35 dB, 10백분위 + 6 dB)를
넘는 마지막 창의 끝으로 측정했다(4.2절과 같은 정의). 이 절의 수치는 두 화자 절반을 모두 본 것이다.

- **끝 출력 위치.** 538에서 자기 문장이 '요'로 끝나는 102클립은 모두(100%) 강제정렬의 마지막 ㅛ가 파일의 마지막 두 프레임에 놓였다.
  끝 무음이 0.04초인 클립도, 0.31초인 클립도 같았다. 탐욕 복호에서도 ㅛ는 말소리 끝 뒤(대부분 마지막 프레임)에서만 나온 클립이
  65개였다. 말소리 안에서 p(ㅛ)가 0.5를 넘는 프레임이 하나라도 있는 클립은 61.8%였다. '요'가 아닌 끝 모음은 18.1%만 마지막 두
  프레임에 놓였다. 608 문장 컷은 large-v3 낱말 끝 + 0.35초에서 잘라 끝에 잡음·숨소리가 남아 말소리 끝 측정이 어렵고(측정한 끝 무음
  중앙 0초), 끝 모음이 파일 끝 40 ms 안에 놓인 비율은 '요' 97.8%, 그 밖 80.6%였다.
- **점수.** 끝 모음의 naive(목표 사후확률)는 자기 문장에서 높다(538 '요' 중앙 0.999, 608 '요' 0.997, 다른 모음 538 0.98·608 0.73~0.94).
  채점기도 같은 마지막 프레임에 끝 모음 확률을 몰아 두기 때문이다. 끝 모음을 문장 점수에서 빼면 608 AUC(자기 문장 대 다른 문장 2개,
  `docs/scoring-analyses-2026-10.md`와 같은 짝)는 0.902 → 0.898(절반 0: 0.940 → 0.934, 절반 1: 0.857 → 0.855), 538은 0.998 그대로였다.
- **코칭.** 앱의 약한 소리 규칙(`main._weak_phones`)이 끝 모음을 짚은 비율은 자기 문장 538 11.3%, 608 9.1%이고, 끝이 아닌 모음의
  음소당 비율은 538 5.8%, 608 9.4%였다. 538의 끝 모음 지목은 대부분 '요'가 아닌 반말 끝 모음(ㅓ·ㅐ·ㅏ·ㅑ)에서 나왔다.
- **녹음 끝 무음.** 앱은 사용자가 정지 버튼을 눌러 녹음을 끝내고(`SpeakingPractice.jsx`), 보내기 전에 끝 무음을 자르지 않는다. 그래서
  실제 녹음은 538·608 컷보다 끝 무음이 길다. 608 한 클립에 1초 끝 소리를 붙여 맥에서 확인하니 끝 ㅏ가 붙인 소리의 끝(4.52초)으로
  옮겨 갔고, 같은 정렬로 계산한 말 빠르기(`speak_cues.rate_pause`, 문장 단계의 S7 지표)가 4.67에서 3.50음절/초로 떨어졌다. 구간 제약
  (4절 M3)으로 말소리 안에 묶으면 그 ㅏ의 naive가 0.0002가 되었다.

해석(가설). 끝 토큰 출력이 소리 내용이 아니라 입력의 끝에 묶여 있다. 그러면 채점 점수 자체는 크게 틀어지지 않을 수 있지만, 끝 모음의
시각(아바타·입모양 비교·말 빠르기)은 녹음 끝 무음 길이만큼 늦어진다. 이 관찰로는 앱 조건(긴 끝 무음)에서 점수·코칭이 얼마나
바뀌는지 알 수 없으므로 5절에서 측정한다. 끝 모음 제외(M4)의 원래 소리 수치는 두 절반을 모두 이미 보았으므로, M4의 판정은
끝 소리를 붙인 조건(T)에 한해 의미가 있다.

## 2. 원인 가설과 확인 방법

| 가설 | 확인 | 판정 규칙 |
|---|---|---|
| H1 학습 자료의 문장 끝 처리 | Zeroth-Korean(정렬기·채점기와 그 바탕 kresnik 모델의 학습 자료) test 500·train 앞 1,000발화의 끝 무음 길이, 같은 발화에서 끝 토큰이 마지막 두 프레임에 나오는 비율 | Zeroth 끝 무음 중앙이 100 ms 이하이고 Zeroth에서도 끝 토큰이 마지막 두 프레임에 나오는 비율이 50% 이상이면 '학습 자료의 끝이 말소리 끝과 붙어 있어 끝 출력이 입력 끝에 묶였다'를 지지한다 |
| H2 끝 무음 길이 | 538 600클립을 그대로(R), 끝에 1초 잡음(T), 끝에 1초 디지털 무음(Z)으로 넣어 끝 토큰 출력 프레임 | T·Z에서 '요' 끝 클립의 끝 토큰이 마지막 두 프레임에 나오는 비율이 R과 5%p 안이면 '무음 길이와 상관없이 입력 끝에 나온다' |
| H3 CTC 빈칸 우세 | 말소리 안에서 p(끝 토큰) > 0.5인 프레임이 있는 클립 비율 | 이 비율이 80% 미만이면 말소리 안에서 빈칸이 끝 모음을 누른다고 본다(1절 관찰 61.8%) |
| H4 int8 양자화 | 같은 클립을 fp32 정렬기(`liplab-lab/models/dgop_ours_2026-09-25/aligner`)로 | int8과 fp32의 마지막 두 프레임 비율 차가 5%p 안이면 양자화 원인이 아니다 |
| H5 프레임 길이·바탕 모델 | T에서 출력이 붙인 1초(50프레임) 끝으로 옮겨 가는지, 바탕 kresnik 음절 모델(같은 wav2vec2 20 ms 프레임)에서도 같은지 | 출력이 붙인 소리 끝으로 옮겨 가면 프레임 해상도 문제가 아니다. kresnik에서도 '요' 끝 클립의 마지막 두 프레임 비율이 50% 이상이면 미세조정 전부터 있던 성질이다 |

## 4. 수정 후보

### 4.1 후보

| 후보 | 내용 |
|---|---|
| M0 | 지금 앱(비교 기준) |
| M1 | 정렬 전 끝에 200 ms 디지털 무음을 덧붙인다 |
| M2(m) | 정렬 전 소리를 4.2절의 말소리 끝 + m ms에서 자른다(앞은 자르지 않는다). m ∈ {0, 50, 150}은 탐색 절반에서 고른다(5.3절). 시각은 원래 녹음 기준 그대로이고, 말 빠르기는 자르지 않은 녹음으로 계산한다 |
| M3 | 소리는 그대로 넣고, 말소리 끝 + 50 ms 뒤 프레임을 정렬·채점에서 뺀다(끝 음소 구간 제약) |
| M4 | 정렬은 M0 그대로, 끝 모음 하나를 문장 점수와 약한 소리 코칭에서 뺀다(시각은 고치지 않는다) |
| (M5) | 정렬기 재학습. 이번에는 하지 않는다. M1~M4가 모두 떨어지고 H1이 지지될 때 다음 작업으로 남긴다 |

### 4.2 말소리 끝

10 ms 창(겹침 없음) RMS를 dB로 바꾸고 문턱 = max(99백분위 − 35 dB, 10백분위 + 6 dB). 문턱을 넘는 마지막 창의 끝이 말소리 끝이다.
넘는 창이 없거나 창이 3개 미만이면 자르지 않는다. 자른 소리는 0.1초보다 짧게 만들지 않는다.

## 5. 측정과 기준

### 5.1 측정

방법·소리 조건마다(M1·M2·M3는 R과 T 모두에 같은 처리를 한다) 클립의 세 목표 문장을 채점한다. 채점은 배포와 같은 int8 정렬기·채점기와
앵커(`dgop_calibration_ours.json`)이고, 순전파는 GPU(TF32 끔, sound-qa 8.1절에서 CPU와 같은 값임을 확인한 방식)에서 한다.

- 끝 모음: 목표 자모열의 마지막 중성 토큰.
- **끝 모음 늦음** = 끝 모음 시작 − 말소리 끝. 538·608은 R 소리의 4.2절 말소리 끝, 서버 음성은 '길이 − 150 ms'를 쓴다. 늦음 > 100 ms면
  '무음에 놓임'으로 센다.
- 문장 점수: 표시 점수. 608·538 AUC(자기 문장 대 다른 문장), 65점 맞게 말함 불합격률, 65점 다르게 말함 합격률.
- 코칭: `main._weak_phones`와 같은 규칙(내지 않는 ㅎ 제외)으로 자기 문장에서 끝 모음이 지목된 비율. 끝이 아닌 모음의 음소당 지목률도 적는다.
- 말 빠르기: `speak_cues.rate_pause`의 rate(앱이 받은 녹음 전체와 그 정렬). '느림' = rate < 4.08(`RATE_P10`).

### 5.2 결함 확인(M0, 확인 절반 1, 서버 음성은 전체)

- D1 시각: 서버 음성 R에서 끝 모음 무음에 놓임 > 20%, 또는 538 T에서 > 20%이면 시각 결함 확인.
- D2 점수: 608 T의 AUC < R의 AUC − 0.01, 또는 608 T의 맞게 말함 불합격 > R + 2%p이면 점수 결함 확인.
- D3 코칭: 538이나 608에서 T의 끝 모음 지목률 > R + 3%p이면 코칭 결함 확인.
- D4 말 빠르기: 538 같은 클립의 rate(T)/rate(R) 중앙 < 0.97, 또는 538 T의 '느림' 비율 > R + 5%p이면 지표 결함 확인.

### 5.3 M2의 m 고르기(탐색 절반 0)

m ∈ {0, 50, 150} 가운데 절반 0에서 C1(538 절반 0과 서버 음성)과 C2(절반 0의 608 AUC, R·T 모두 ≥ M0 R − 0.01)를 함께 만족하는 가장
큰 m을 고른다(약한 끝소리를 덜 자르는 쪽). 하나도 없으면 m = 50으로 확인 절반에 간다. 탐색 절반에서는 다른 후보도 모두 보고만 한다.

### 5.4 후보 기준(확인 절반 1, R과 T 모두)

- C1 시각: 서버 음성 끝 모음 무음에 놓임 ≤ 5%, 538 끝 모음 무음에 놓임 ≤ 5%. (538 기준은 M2·M3가 잘라 내는 기준과 같은 말소리 끝이라
  순환적이다. 그래서 독립 기준인 서버 음성을 함께 본다.)
- C2 608 AUC ≥ M0 R AUC − 0.01.
- C3 608 맞게 말함 불합격 ≤ M0 R + 2%p, 608 다르게 말함 합격 ≤ 5%, 538 AUC ≥ 0.99, 538 맞게 말함 불합격 ≤ M0 R + 1%p,
  538 다르게 말함 합격 ≤ 1%.
- C4 코칭: 538·608 각각 끝 모음 지목률 ≤ M0 R + 2%p.
- C5 말 빠르기: 538 rate(그 방법 T)/rate(그 방법 R) 중앙이 0.97~1.03, 538 T '느림' 비율 ≤ M0 R + 2%p.
- C6 서버 음성 자기 문장 점수 평균 ≥ M0 R − 1.0.

### 5.5 채택 규칙

1. M1·M2(5.3에서 고른 m)·M3 가운데 C1~C6을 모두 만족한 것을 후보로 하고, 여럿이면 M2 > M3 > M1 순으로 고른다(입력을 줄이는 M2가 가장
   단순하고 빠르다).
2. 하나도 없으면, D2나 D3가 확인되었고 M4가 C2·C3·C6을 만족할 때만 M4를 점수·코칭에 넣는다(시각 결함은 결과 절에 남긴다).
   D2·D3가 모두 확인되지 않았으면 M4를 넣지 않는다(끝 모음은 지금 문장 점수에 정보를 조금 더한다, 1절).
3. 그 밖이면 코드를 바꾸지 않는다.
4. 채택한 방법은 `dgop_acoustic`에 넣고, 맥에서 파드 결과와 같은 값이 나오는지 클립 몇 개로 확인한 뒤 테스트를 붙인다.

### 5.6 함께 정리할 것(채택했을 때)

- 서버 음성 음절 시각: 지금 목록은 `qa_rules.fix_tail_syllables`(sound-qa 8.3)로 고친 시각이다. 채택한 방법은 `phone_confidences`에
  들어가므로 다음 점검·합성부터 적용된다. 채택한 방법의 서버 음성 정렬에서 `fix_tail_syllables`가 바꾸는 클립 비율을 보고하고,
  지금 목록은 다시 만들지 않는다(소리와 이름이 바뀌지 않는 한 음절 시각만 바꿀 이유가 약하다).
- 말 빠르기 기준(`RATE_P10/50/90`)은 538 자료에서 정한 것이다. 채택한 방법의 538 R 중앙 rate가 M0 R과 3% 넘게 다르면 결과 절에
  적고, 기준 다시 정하기는 S7 문서와 함께 따로 한다.

## 6. 절차와 비용

- 맥: `scripts/dgop_tail_pod/build_jobs.py`(작업 목록), `session.sh stage`(묶음). 파드: `session.sh launch`가 liplab-lab의
